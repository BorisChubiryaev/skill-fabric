# Выгрузка задач из Jira Server / Data Center через MCP

Справочник для агента. Читай перед шагом выгрузки. Цель — собрать выборку, по
которой метрики будут корректны, и не сжечь контекст на тысячах задач.

## Поиск нужного инструмента MCP

Имена инструментов различаются между серверами Atlassian MCP. Нужен тот, что
принимает **JQL**; типичные названия содержат `jira` и `search`. Проверь доступ
дешёвым вызовом (`maxResults=1`) до основной выгрузки: так ошибка прав или
неверный ключ проекта всплывёт сразу.

Полезны также инструменты, отдающие поля проекта и статусы, — но обязателен
только поиск по JQL.

## Какие задачи брать

Главная ошибка — взять только созданные за период. Для потока нужны все задачи,
которые в окне **жили**: создавались, закрывались или двигались.

```sql
project = ABC AND (
  created  >= "2026-06-01" OR
  resolved >= "2026-06-01" OR
  updated  >= "2026-06-01"
) ORDER BY created ASC
```

Варианты рамок:

```sql
-- по доске (сначала узнай фильтр доски) либо по готовому фильтру
filter = 12345 AND updated >= -90d

-- ограничить людьми
project = ABC AND assignee in ("ivan.petrov","maria.sokolova") AND updated >= -90d

-- включая задачи без исполнителя
project = ABC AND (assignee is EMPTY OR assignee in (...)) AND updated >= -90d

-- исключить подзадачи, если они шумят
project = ABC AND type != Sub-task AND updated >= -90d
```

`ORDER BY created ASC` даёт стабильный порядок страниц — без сортировки при
пагинации возможны пропуски и дубли.

## Поля и история изменений

Запрашивай поля явно — так ответ меньше и предсказуемее:

```
summary, issuetype, status, priority, assignee, reporter,
created, updated, resolutiondate, duedate, labels, components, issuelinks
```

Плюс, если нужны спринты и оценки, — соответствующие `customfield_*`
(в Jira DC спринт лежит в customfield строкой
`...greenhopper.service.sprint.Sprint@..[id=5,name=Спринт 3,...]`, story points
обычно `customfield_10002`; скрипт распознаёт оба варианта, а точное имя поля
можно передать через `--story-points-field`).

**История изменений:** `expand=changelog`. Без неё нельзя посчитать время цикла
(момент перехода в работу) и построить точный CFD.

На практике многие серверы MCP отдают задачи **без** changelog, даже когда
`expand` передан, и не умеют отдавать историю пакетом. Поштучный обход — главный
источник многочасового ожидания, поэтому действуй так: **бери историю только по
закрытым за период задачам** (именно они дают время цикла), а не по всей
выборке, и обязательно укажи фактическое покрытие в отчёте. Частичное покрытие —
нормальный, честный результат; молчаливая поштучная выгрузка всего — нет.

Порядок действий:

1. Проверь покрытие после `normalize` — поле `changelog_coverage_pct`.
2. Если покрытие низкое, попробуй выгрузить историю статусов отдельным запросом
   (у большинства серверов есть инструмент истории/переходов по задаче).
3. Сложи её в файл и передай штатным флагом — **не пиши свой скрипт слияния**:

```bash
python3 scripts/jira_analytics.py normalize raw_*.json \
  --transitions transitions.json --out issues.json
```

Формат `transitions.json` — любой из двух:

```json
{ "ABC-1": [ {"at": "2026-06-01T10:00:00+0300", "from": "Open", "to": "In Progress"} ] }
```

```json
[ {"key": "ABC-1", "created": "...", "fromString": "Open", "toString": "In Progress"} ]
```

Скрипт подставит историю только тем задачам, у которых её ещё нет, и покажет в
выводе `changelog_merged_from_file`. Если и так не получилось — продолжай без
истории и предупреди пользователя: скрипт оценит CFD по датам создания/решения,
а время цикла считать не станет.

**Осторожно с масками файлов.** Если складываешь выгрузки как `raw_1.json`,
`raw_2.json`, а результат слияния — как `raw_with_cl.json`, то маска `raw_*.json`
подхватит и его: получишь задачи в двойном размере и тихо испорченные метрики.
Именуй промежуточные файлы так, чтобы они не попадали под маску входных.

## Пагинация

Jira DC отдаёт результат порциями. **Имена полей зависят от сервера MCP:** в
одних ответах это `startAt`/`maxResults`, в других — `start_at`/`max_results`.
Не полагайся на память: посмотри, что реально пришло в ответе. Тяни, пока
выгруженное меньше `total`:

```
startAt=0    maxResults=100
startAt=100  maxResults=100
...
```

**Сервер молча урезает размер страницы, и предсказать его нельзя.** В реальных
прогонах на запрос со `maxResults=100` приходило `max_results: 21`, а иногда и
`max_results: 2` — MCP режет ответ по объёму, а не по числу задач. Поэтому:

- **никогда не считай, что получил столько, сколько попросил.** Смещение для
  следующей страницы = предыдущее смещение **плюс фактическое число задач в
  ответе**, а не плюс запрошенный размер. Иначе выгрузка пойдёт с дырами;
- продолжай, пока сумма выгруженного меньше `total`;
- если ответ вернул 0 задач при недостигнутом `total` — останови цикл и скажи
  об этом, иначе получится бесконечный цикл.

**Сверь итог с `total`**: расхождение означает потерянные страницы и тихо
испорченные метрики.

Каждый ответ сохраняй отдельным файлом (`raw_1.json`, `raw_2.json`, …) и передай
их все команде `normalize` — она склеит и уберёт дубли:

```bash
python3 scripts/jira_analytics.py normalize raw_*.json --out issues.json
```

## Иерархия: эпики и подзадачи

Чтобы связи определились, в выборку должны попасть и сами эпики, и задачи под
ними. Практичнее всего не фильтровать по типу вовсе, а исключать подзадачи
только если они реально мешают:

```sql
-- эпики и задачи вместе (рекомендуется)
project = ABC AND updated >= -90d

-- только если подзадачи создают шум и дублируют учёт
project = ABC AND type != Sub-task AND updated >= -90d
```

Нужные поля: `parent` (для подзадач и, в новых Jira, для детей эпика) и поле
**Epic Link**. Его номер различается между инсталляциями (`customfield_10014`,
`customfield_10000`, …). Скрипт определяет его сам — по значению вида `ABC-123`
в customfield, — но если связи не нашлись, укажи поле явно:

```bash
python3 scripts/jira_analytics.py normalize raw_*.json \
  --epic-link-field customfield_10014 --out issues.json
```

Проверь блок `hierarchy` в выводе `normalize`: `epics`, `subtasks`,
`linked_to_epic`, `orphans`. Если `linked_to_epic` равен нулю при заведомо
существующих эпиках — поле Epic Link не то, задай его явно.

## Когда в выборке нет ни одной открытой задачи

Набор «рабочих» статусов скрипт выводит из текущих статусов выборки. Если
команда закрыла всё (WIP = 0), рабочих статусов среди текущих нет, и определить
момент начала работы не по чему. Скрипт в этом случае берёт запасной путь —
первый переход, который не ведёт сразу в «готово», — и помечает это в
`flow.cycle_time_method`.

Чтобы посчитать точно, передай названия рабочих статусов явно:

```bash
python3 scripts/jira_analytics.py analyze issues.json --out metrics.json \
  --wip-statuses "В работе,На ревью,Тестирование"
```

## Сколько это стоит по времени

Расчёт быстрый: 2000 задач считаются меньше секунды. Долгим бывает только
общение с MCP, и решает тут **число запросов**, а не объём данных.

| Приём | Запросов на 800 задач |
|---|---|
| Страницами по 100 | ~8 |
| Страницами по 50 | ~16 |
| История изменений по одной задаче | **+800** ← так делать нельзя |

Отсюда правила: страницы по 100; историю — только пакетно (`expand=changelog`);
если пакетно никак, брать её лишь для **закрытых за период** задач, а не для
всех. Поштучный обход задач ради changelog — главная причина, по которой отчёт
приходится ждать часами.

## Объём

Ориентир: до ~2000 задач конвейер считает быстро. Если выборка сильно больше:

- сократи период или ограничь типы задач (`type != Sub-task`);
- разбей по компонентам и собери несколько дашбордов;
- помни, что перцентили устойчивы уже на сотнях задач — «все задачи за три года»
  редко дают больше смысла, чем последний квартал.

Никогда не пересказывай выгрузку в контекст целиком: файлы → скрипт → метрики.

## Особенности Jira DC, о которые легко споткнуться

- **Категория статуса** приходит в `fields.status.statusCategory.key` и
  принимает значения `new` / `indeterminate` / `done`. Названия статусов у
  каждой команды свои, а категории — стандартные, поэтому расчёт опирается на них.
- **`resolutiondate` может быть пустым** у формально закрытых задач, если
  резолюция не проставлена. Тогда задача считается открытой — это отражает
  реальный учёт, а не ошибку скрипта.
- **Блокеры** распознаются тремя способами: флаг (`Impediment` в customfield),
  связь `is blocked by` и название статуса, похожее на «Blocked»/«Заблокировано».
- **Часовые пояса**: DC отдаёт смещение вида `+0300`; скрипт это понимает.
- **Переоткрытые задачи** дают несколько переходов в работу; временем начала
  считается первый переход — это делает cycle time консервативным (не
  занижает его).

## Быстрая проверка без Jira

Чтобы убедиться, что конвейер и дашборд работают, есть синтетические данные:

```bash
python3 scripts/jira_analytics.py demo --out raw_demo.json --count 180 --days 120
python3 scripts/jira_analytics.py normalize raw_demo.json --out issues.json
python3 scripts/jira_analytics.py analyze issues.json --out metrics.json
python3 scripts/jira_analytics.py render metrics.json --out dashboard.html --issues issues.json
```

Формат `demo` совпадает с ответом `/rest/api/2/search`, поэтому проверяет ровно
тот же путь нормализации, что и реальные данные.
