# Аналитический слой: как модель участвует в анализе

Справочник для агента. Читай перед шагом анализа.

## Зачем этот слой

Алгоритмы находят только то, что заранее описано порогом: «WIP ≥ 3», «не
обновлялось 14 дней». Они не читают названия задач, не видят сюжетов и не
отличают следствие от причины. В реальном разборе самое ценное выглядит так:

- «Четыре эпика висят в работе годами — это не работа, а контейнеры; они портят
  CFD всей команды»;
- «max 574 дня — это одна задача, две трети срока пролежавшая в Need Info, а не
  медленная разработка»;
- «Десять квартальных эпиков заведены и не начаты — бэклог оформлен, но не
  запущен».

Ни одно из этих наблюдений не выводится из порогов. Их делает модель, читая
названия, даты и связи. **Твоя аналитическая работа — обязательная часть отчёта,
а не украшение к нему.**

Чтобы эта работа была проверяемой, конвейер разделён на три шага:

```
brief  →  ты пишешь insights.json  →  validate-insights  →  render --insights
факты      интерпретация              заземление            публикация
```

## Шаг 1. Получи выжимку фактов

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" brief metrics.json --out brief.json
```

`brief.json` — это компактная сводка (обычно 20–40 КБ): числа, тренды, метрики
ожидания, качество учёта и **образцы задач с названиями**. Названия здесь
главное: именно по ним видны темы. Читай выжимку целиком — она специально
сделана такой, чтобы поместиться в контекст вместо тысяч задач.

Внутри есть два служебных раздела: `questions_to_answer` (о чём подумать) и
`rules_for_you` (ограничения, которые нельзя нарушать).

## Шаг 2. Напиши insights.json

Схема:

```json
{
  "executive_summary": "2–4 предложения для руководителя: что происходит и что с этим делать",
  "findings": [
    {
      "title": "Короткий заголовок находки",
      "severity": "critical | serious | warning | info | good",
      "observation": "Что видно в данных — только факты из выжимки",
      "interpretation": "Что это значит для команды — твой вывод",
      "recommendation": "Что конкретно сделать",
      "evidence_keys": ["ABC-12", "ABC-40"],
      "confidence": "high | medium | low"
    }
  ],
  "next_steps": ["Конкретное действие 1", "Конкретное действие 2"]
}
```

Все поля кроме `evidence_keys` обязательны; проверка их требует.

### Правила, которые делают выводы полезными

1. **Числа только из выжимки.** Не пересчитывай и не округляй заново: расхождение
   отчёта с дашбордом мгновенно убивает доверие ко всему документу.
2. **Каждая находка — со ссылками на задачи.** `evidence_keys` превращают мнение
   в проверяемое утверждение. Находка с `confidence: high` без ссылок не пройдёт
   проверку — и это правильно.
3. **Не пересказывай `computed_warnings`.** Они и так попадут в отчёт отдельным
   разделом. Твоя задача — углубить их: объяснить причину, связать между собой,
   отделить следствие от источника.
4. **Ищи одну корневую проблему.** Пять равнозначных находок читаются как шум.
   Гораздо ценнее сказать: «вот это тянет за собой остальное».
5. **Рекомендация должна быть выполнимой на этой неделе.** «Улучшить процесс» —
   не рекомендация. «Ввести правило: нет ответа в Need Info 3 дня → эскалация» —
   рекомендация.
6. **Не хватает данных — так и скажи.** Ставь `confidence: low` и назови, чего
   не хватает. Честная неопределённость полезнее уверенной выдумки.
7. **Люди — это нагрузка и риск, а не рейтинг.** Формулируй так, чтобы отчёт
   можно было показать самой команде.

### Где искать сюжеты

- **Названия зависших и ожидающих задач** — повторяющиеся слова выдают тему:
  общий компонент, одного заказчика, один тип работы.
- **Выбросы времени цикла** — почти всегда у них своя история; посмотри, что это
  за задачи и сколько они пролежали в ожидании.
- **Типы задач** — эпики и «разное» ведут себя иначе, чем обычные задачи, и часто
  портят статистику.
- **Качество учёта** — пачковые и мгновенные закрытия означают, что метрики
  времени описывают Jira, а не работу. Если их много, скажи об этом **до** любых
  выводов о скорости.
- **Связка «ожидание ↔ люди»** — если задачи ждут, узкое место не в исполнителях.

## Шаг 3. Проверь заземление

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" validate-insights insights.json \
  --issues issues.json
```

Проверка ловит: пустые обязательные поля, недопустимые `severity`/`confidence`,
ссылки на несуществующие задачи и уверенные утверждения без доказательств.
Продолжай только при `"ok": true`. Замечания — не формальность: несуществующий
ключ задачи в отчёте руководителю дороже, чем лишняя минута на исправление.

## Шаг 4. Опубликуй

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" render metrics.json \
  --out dashboard.html --issues issues.json --insights insights.json --title "..."
```

Твой анализ встанет **первым разделом** дашборда — до графиков и расчётных
предупреждений, потому что ради него отчёт и читают. Разделение подписано явно:
интерпретация модели отделена от детерминированных чисел, чтобы читатель
понимал, где факт, а где вывод.
