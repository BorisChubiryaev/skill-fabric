# Глубокая аналитика Jira → автономный HTML-дашборд

## Язык общения

Всё общение с пользователем — **по-русски**: уточняющие вопросы, статусы, выводы,
итоговый ответ. Дашборд тоже собирается на русском. Технические команды, JQL,
имена полей и путей остаются как есть.

## Назначение

Собери из Jira (Server / Data Center) честную картину работы команды: как течёт
поток задач, сколько времени они реально живут, кто чем загружен, где затыки — и
оформи это в **самодостаточный HTML-файл**, который открывается без интернета и
которым можно поделиться с руководителем.

Ценность здесь не в том, чтобы показать графики, а в том, чтобы **назвать
проблемы и их следствия**. «Cycle time p85 = 21 день» — это число. «Треть задач
висит в работе дольше 21 дня, обычно это скрытый блокер или слишком крупная
задача» — это вывод, с которым можно идти на встречу команды.

Работа делится на две части, и обе обязательны:

- **Считает скрипт** `scripts/jira_analytics.py` — метрики, пороговые правила,
  графики. Числа должны быть воспроизводимыми, поэтому не считай ничего «в уме»
  по выгрузке.
- **Анализируешь ты** — читаешь названия задач, находишь сюжеты, объясняешь
  причины выбросов и отделяешь следствия от корневой проблемы. Пороговые правила
  этого не умеют; без твоего разбора отчёт остаётся набором чисел.

Скрипт — чёрный ящик с документированным CLI: **не читай и не пересказывай его
исходник**, это только тратит контекст. Всё, что нужно знать, есть в этом файле
и в `references/`; при сомнениях запусти команду с `--help`.

## Обязательный процесс

### 1. Уточни рамки анализа — до выгрузки

Пользователь обычно даёт ссылку на проект/доску или просто название. Не
угадывай остальное: объём выгрузки и смысл выводов зависят от рамок.

**Задавай вопросы через интерактивный инструмент вопросов с вариантами ответа**
(в разных средах он называется по-разному; в Claude Code это `AskUserQuestion`).
Одним вызовом, все вопросы сразу, у каждого — готовые варианты и возможность
вписать своё. Так пользователь выбирает мышью за несколько секунд, а не
перепечатывает ответы на четыре пункта.

Списком в чате спрашивай **только если такого инструмента в среде нет** — это
запасной вариант, а не основной.

Вопросы:

1. **Что анализируем** — ключ проекта (`ABC`), доска, готовый фильтр или свой JQL.
   Из ссылки вида `.../projects/ABC/...` или `.../RapidBoard.jspa?...` ключ
   обычно виден — предложи его и попроси подтвердить.
2. **За какой период** — например, последние 90 дней или конкретные даты.
   По умолчанию предложи 90 дней: этого хватает на устойчивые перцентили.
3. **Кого включаем** — всю команду или только конкретных людей; учитывать ли
   задачи без исполнителя.
4. **Что важнее всего** — скорость поставки, загрузка людей или риски и блокеры.
   Ответ определит, на чём сделать акцент в выводах.

Если пользователь говорит «делай как считаешь нужным» — бери проект целиком,
90 дней, всех исполнителей и скажи, какие рамки взял.

### 2. Найди инструменты MCP и подтверди доступ

Имена инструментов у разных серверов Atlassian MCP отличаются. Сначала посмотри,
какие инструменты доступны, и выбери тот, что умеет **поиск по JQL**. Проверь
доступ дешёвым запросом (одна задача, `maxResults=1`), прежде чем тянуть тысячи.

Если JQL-инструмента нет вовсе — остановись и скажи об этом: без поиска по JQL
собрать корректную выборку нельзя.

### 3. Выгрузи задачи

Справочник `references/jql-and-fetching.md` содержит готовые JQL, список полей,
пагинацию и особенности Jira DC. Открывай его, когда нужен точный синтаксис или
что-то пошло не так, — не перечитывай целиком на каждом запуске.

Ключевое, что легко сделать неправильно:

- **Бери задачи, а не только созданные за период.** Для потока нужны и те, что
  созданы раньше, но закрывались или двигались внутри окна.
- **Запрашивай `expand=changelog`.** Без истории изменений нельзя посчитать
  время цикла и построить CFD — скрипт честно об этом скажет, но отчёт станет
  беднее. Если MCP-инструмент не умеет `expand`, продолжай без него и предупреди
  пользователя, что cycle time посчитан не будет.
- **Пагинируй до конца.** Jira отдаёт порциями; частичная выгрузка тихо исказит
  все метрики. Имена полей зависят от сервера MCP: встречаются и `startAt`/
  `maxResults`, и `start_at`/`max_results` — смотри, что реально пришло в ответе,
  и сверяй сумму выгруженного с `total`.
- **Если changelog не приходит вместе с задачами**, выгрузи историю статусов
  отдельно и передай её файлом в `normalize --transitions` (формат — в
  `references/jql-and-fetching.md`). Не пиши для этого свой скрипт слияния.
- **Складывай сырые ответы в файлы** (`raw_1.json`, `raw_2.json`, …), а не держи
  в контексте: скрипт прочитает их сам, а ты не потратишь окно на тысячи задач.

### 3.5. Держи бюджет: главный источник многочасового ожидания

Расчёт занимает секунды даже на тысячах задач — время съедают **вызовы MCP**.
Дорогое здесь только одно: количество запросов.

- **Никогда не запрашивай историю изменений по одной задаче в цикле.** Это
  самая частая причина ожидания на часы: 800 задач = 800 запросов. История
  нужна только скопом (`expand=changelog`) либо одним запросом на пачку. Если
  так не выходит — возьми историю **только для закрытых за период** задач
  (именно они дают время цикла), а не для всей выборки, и укажи в отчёте
  фактическое покрытие. Частичное покрытие — нормальный честный результат.
- **Тяни страницами по 100** — но помни, что сервер молча урежет: на запрос
  «100» реально приходит и 21, и 2. Смещение следующей страницы считай по
  **фактическому** числу задач в ответе, иначе выгрузка пойдёт с дырами. Пробный
  запрос с `maxResults=1` делай ровно один раз, для проверки доступа.
- **Ограничивай выборку.** Ориентир — до ~1500 задач. Если JQL возвращает
  больше, не тяни молча: сократи период или типы задач и **скажи пользователю,
  какие рамки взял** (либо спроси, если разница принципиальная).
- **Не выгружай поля, которые не используешь.** Список нужных полей — в
  справочнике по выгрузке.
- **Считай запросы.** Если их уже больше ~30, остановись и пересмотри подход:
  почти наверняка ты делаешь поштучные вызовы там, где нужен один пакетный.

Если выгрузка всё же обещает быть долгой, скажи об этом до начала, а не после.

### 4. Приведи к канону и посчитай

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" normalize raw_*.json --out issues.json
python3 "$SKILL_ROOT/scripts/jira_analytics.py" analyze issues.json --out metrics.json \
  --granularity week --since 2026-06-01 --stale-days 14 --wip-warn 3
```

`normalize` понимает разные формы ответов MCP (`{"issues":[…]}`, массив, JSONL),
убирает дубли и сообщает **покрытие changelog** — посмотри на него: если оно
низкое, скажи об этом пользователю, а не выдавай время цикла как надёжное.

`analyze` считает метрики и прогоняет правила предупреждений. Пороги
подстраивай под контекст: `--wip-warn` (сколько задач в работе на человека
считать перегрузом), `--stale-days`, `--longlived-days`, `--granularity`
(`day`/`week`/`month` — для периода до месяца бери дни).

### 4.5. Учти иерархию: эпики, задачи, подзадачи

Скилл сам разбирает связи: эпик ↔ задача (через Epic Link или `parent`) и
подзадача ↔ родитель, причём подзадача наследует эпик своей задачи. После
`normalize` посмотри блок `hierarchy`: сколько эпиков, подзадач и задач вне
эпиков.

По умолчанию (`--scope-items leaf`) **эпики исключены из метрик потока**: эпик —
контейнер, а не единица работы, и если считать его наравне с задачей, объём
завышается, а хвост времени цикла раздувается. Сам разрез по эпикам при этом
никуда не девается — он считается отдельно и отвечает на вопрос «что с
инициативами»: прогресс, простой, блокеры и нестыковки вроде «эпик закрыт, а
задачи под ним открыты».

Если Epic Link лежит в нестандартном поле и связи не определились, передай его
явно: `normalize --epic-link-field customfield_10014`.

### 5. Проведи собственный анализ — это обязательный шаг

Схема выводов и правила — в `references/ai-insights.md`; открой его, если
работаешь со скиллом впервые или сомневаешься в формате. Дальше:

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" brief metrics.json --out brief.json
```

`brief.json` — компактная выжимка фактов **с названиями задач**. Прочитай её и
найди то, чего пороги не видят: повторяющиеся сюжеты в названиях зависших задач,
что на самом деле стоит за выбросами времени цикла, отражают ли метрики работу
или практику ведения Jira, какая одна проблема тянет за собой остальные.

Оформи выводы в `insights.json` по схеме из справочника и обязательно проверь:

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" validate-insights insights.json \
  --issues issues.json
```

Проверка не даёт сослаться на несуществующую задачу и требует доказательств под
уверенными утверждениями. Продолжай только при `"ok": true`.

Не пропускай этот шаг «ради скорости»: расчётные предупреждения — это пороги,
а разбор причин есть только у тебя.

### 6. Собери дашборд

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" render metrics.json \
  --out dashboard.html --issues issues.json --insights insights.json \
  --title "Аналитика проекта ABC"
```

Посмотреть, что получилось, можно одной командой — не пиши для этого свой
скрипт разбора JSON:

```bash
python3 "$SKILL_ROOT/scripts/jira_analytics.py" summary metrics.json
```

Если время цикла посчиталось по нулю задач при наличии истории — почти наверняка
в выборке нет ни одной открытой задачи, и рабочие статусы не из чего вывести.
Передай их явно: `analyze --wip-statuses "В работе,На ревью"`. Поле
`flow.cycle_time_method` показывает, каким способом посчитано.

`--issues` нужен для гистограммы времени цикла, `--insights` ставит твой анализ
первым разделом отчёта. Результат — один HTML без внешних зависимостей:
открывается офлайн, переживает пересылку почтой, работает в светлой и тёмной теме.

### 7. Проверь результат, прежде чем отдавать

- `analyze`, `validate-insights` и `render` завершились с кодом `0` и `"ok": true`;
- число задач в `metrics.json` совпадает с тем, сколько вернула Jira (если
  меньше — выгрузка оборвалась на пагинации, вернись к шагу 3);
- HTML непустой и не содержит `http://`/`https://` (то есть действительно
  автономный);
- если есть возможность отрендерить страницу — открой и посмотри: нет ли
  наложений подписей и пустых секций.

### 8. Дай выводы словами

Не ограничивайся ссылкой на файл. В ответе:

- назови 3–5 главных находок из раздела предупреждений, начиная с критических,
  и объясни, **что они означают для команды**;
- приведи опорные числа (пропускная способность, cycle time p50/p85, bus factor);
- честно укажи ограничения: покрытие changelog, рамки выборки, что не вошло;
- предложи следующий шаг (что стоит разобрать вручную).

Дашборд — материал для разговора, а твой ответ — сам разговор.

## Как читать метрики

Полные определения и правила предупреждений — в `references/metrics.md`.
Коротко о том, что чаще всего трактуют неверно:

- **Lead time** (создание → закрытие) включает ожидание в бэклоге;
  **cycle time** (начало работы → закрытие) — только саму работу. Их разрыв
  показывает, сколько задача просто ждёт.
- **Смотри на p85, а не на среднее.** Среднее прячет хвост, а обещания срокам
  дают именно по хвосту.
- **Растущая полоса «в работе» на CFD** — работу начинают быстрее, чем
  заканчивают; почти всегда это причина роста времени цикла.
- **Bus factor** — сколько людей делают половину объёма. Единица означает
  хрупкость, а не эффективность.

## Границы и честность

- Инструмент считает то, что есть в Jira. Если команда не ведёт статусы честно,
  метрики отразят учёт, а не реальность, — скажи об этом, если видите признаки
  (например, задачи закрываются пачками в конце спринта).
- Оценка людей по числу закрытых задач **не является оценкой продуктивности**:
  задачи разного размера. Подавай распределение как сигнал о нагрузке и рисках
  концентрации, а не как рейтинг сотрудников.
- Без `changelog` нет времени цикла и точного CFD — не подставляй правдоподобные
  числа вместо отсутствующих.
- Данные не покидают машину: скрипт работает офлайн. Это важно, если в задачах
  есть чувствительная информация.

## Когда остановиться без результата

Остановись и назови причину, если нет MCP-инструмента с поиском по JQL, доступ к
проекту закрыт, выборка пуста (проверь JQL и период) или выгрузка оборвалась и
её нельзя достроить. Пустой или частичный дашборд хуже, чем честное «не смог».

## Типичные ошибки

| Ошибка | Правильное действие |
|---|---|
| Начать выгрузку, не уточнив период и рамки | Задать 4 вопроса из шага 1 одним сообщением |
| Выгрузить только созданные за период | Захватить и закрытые/обновлённые в окне |
| Забыть `expand=changelog` | Запросить историю; без неё честно сказать про cycle time |
| Оборвать пагинацию | Тянуть до конца и сверить итоговое число с `total` |
| Считать метрики «на глаз» по выгрузке | Считать только скриптом — числа должны воспроизводиться |
| Держать тысячи задач в контексте | Складывать сырые ответы в файлы |
| Спрашивать рамки списком в чате | Использовать интерактивный выбор с вариантами |
| Тянуть историю изменений по задаче за запрос | Только пакетно; иначе часы ожидания |
| Молча выгружать десятки тысяч задач | Ограничить рамки и сказать, какие взял |
| Считать эпик такой же единицей работы, как задачу | Оставить `--scope-items leaf` |
| Отдать ссылку на файл без выводов | Назвать находки словами и объяснить последствия |
| Пропустить шаг анализа, ограничившись порогами | Прогнать `brief` → `insights.json` → `validate-insights` |
| Читать исходник `jira_analytics.py` | Это чёрный ящик; смотреть `--help` и `references/` |
| Писать свой скрипт слияния истории статусов | Использовать `normalize --transitions` |
| Писать свой скрипт связей задача→эпик | Использовать `normalize --epic-links` |
| Писать свой скрипт разбора metrics.json | Использовать команду `summary` |
| Считать смещение страницы по запрошенному размеру | Считать по фактически полученному числу задач |
| Сослаться в выводах на несуществующую задачу | Прогнать `validate-insights` до публикации |
| Подать список закрытых задач как рейтинг людей | Подавать как нагрузку и риск концентрации |
